# BK3633 Components

`native_component_src/bk3633` 保存可被多个 BK3633 board 和 image 复用的 SDK runtime、显式 SDK source manifest 与 PAL backend。物理 Board wiring 和 linker layout 约束不属于 component；SDK role、capacity、Stack/BIM/OAD 选择和 configuration header 属于最终 firmware project/image。

## Ownership

```text
BK3633 SDK
    -> native_component_src/bk3633
    -> boards/<board>/bk3633
    -> projects/<group>/targets/bk3633_firmware/<image>/<board>
```

- `sdk_build` 显式列出固件 closure 需要的 SDK source，不递归编译整个 SDK。
- `sdk_runtime` 拥有 ROM environment、NVDS、`rwip_init()`、`rwip_schedule()`、预编译 Stack 要求的 `appm_init()` ABI，以及 selected RWIP source 要求的静默 `uart_printf()` ABI。
- `h2_pal_core` 实现 BK3633 memory、log、queue、time、battery、power、system event、BLE Host、Preference 和 Disk PAL provider，并提供带 bounded poll 与 continuous repetition check 的 hardware TRNG entropy callback。Memory provider 独占 allocator、PAL accessor 和统计状态；Board 只注入 linker layout 得出的 image-lifetime RAM 区域。
- `h2_pal_core` 还提供 target-owned completion record queue；IRQ/RWIP 深层回调只记录 owner wait key，root boundary 才把它交给 Board 绑定的 `libs/pal/providers/libco` instance。
- `h2_nfc_fm17660k` 将 board 注入的 raw UART callbacks 适配为可移植 FM17660K register/FIFO transport，并对称管理 UART 与 driver 生命周期；它不拥有 UART instance、pin 或共享供电。
- `boards/<board>/bk3633` 提供 UART、GPIO、clock、RF、watchdog、interrupt、物理 Flash/RAM 约束和可选 linker layout；不能为所有 consumer 选择 BLE role、connection/activity capacity、Stack/BIM/OAD 或 SDK configuration header。
- `projects/<group>/targets/bk3633_firmware/<image>/<board>` 显式选择 image 的 SDK role/capacity、Stack/BIM/OAD、configuration header 和兼容 linker layout；同一 Board 的不同 project 可以选择不同配置。
- 需要 Crypto PAL 的 BSP 直接把 `h2_pal_core` entropy callback 注入 `libs/pal/providers/wolfssl` 的裁剪 `wolfcrypt` provider，不增加 target-specific lifecycle 或 API forwarding wrapper。
- launcher 创建 image-specific `TASK_APP`，拥有 GAPM bootstrap、scheduler loop、deferred Runtime event dispatch 和 release packaging。
- portable app 只调用 Runtime/PAL public wrapper，不 include BK3633 SDK 或 board-private header。

三个 firmware entry 都只从 Bazel `graph` 收集 first-party source owner、public
include root 和 portable archive。Runner 为每次 action 生成 Make include，提供
`H2_BAZEL_NATIVE_SRCS`、`H2_BAZEL_NATIVE_INCLUDES` 与 `H2_BAZEL_ARCHIVES`；共享
Make 只保留 SDK source、compiler/linker、Stack、BIM、layout、merge 和 release
机械，不能再列举 first-party source 或 archive fallback。Libco Smoke 是明确的
诊断 closure，只选择它需要的 Board/PAL owner，避免把 production ISR provider
带入同一个 link。

BK3633 repo 由同级 `firmwares-devenv` checkout 锁定，并通过 `BK3633_PATH` 向调用方
暴露。Launcher 从该 repo 的 `SDK` 解析预编译 Stack BIN/ELF，并直接编译
`SDK/projects/boot_for_all_roles` 的 BIM project。生成的 BIM 只存在于
GizOS local build output。Portable C BinConvert host tool 位于
`tools/bk3633_binconverter`，由 `bk3633_firmware` action 作为 exec tool 注入 native Make，不需要
Docker 或 firmware-devenv host executable。Component 不能包含外部 host executable、
预编译 Stack 或 board-specific BIM source。

显式提供 native ccache runtime locator 时，BK3633 runner 使用Bazel已下载并校验archive与expanded-tree identity的ARM toolchain创建invocation-local compiler wrapper，并让production、Log与Libco Smoke entry共享`bk3633` cache namespace及GCS `ccache/bk` family prefix。SDK source、image configuration、compile flags、included configuration与generated header仍由ccache compile key判定；该prefix与ESP `ccache/esp`、Bazel `firmwares`分离。BIM、预编译Stack、link、merge和release packaging不作为compiler cache object，也不能因cache命中跳过原有probe与artifact validation。

## SDK runtime

`BK3633_PATH` 必须来自共享 provider environment 并指向 BK3633 Git checkout
根目录。Tapdoki launcher 不 source 外部 `export.sh`，也不从
`FIRMWARE_DEVENV_ROOT`、ambient path、个人配置或 GizOS-local vendor checkout 推导路径。
Public header、committed configuration 和 build output 不能保存个人绝对路径。
Launcher、component Makefile 和 CMake entrypoint 都从该 repo root 内部派生
`BK3633_PATH/SDK`；`BK3633_SDK_PATH` 不再是调用方或 provider contract。

`h2_bk3633_sdk_runtime_platform_init()` 完成 board prerequisite 并保存 callback config。随后由 image 创建的 BLE Stack cooperative task 调用 `h2_bk3633_sdk_runtime_task()`；该 task 唯一调用 `rwip_init()` 与 `rwip_schedule()`。ROM setEvent/clearEvent hook 维护 coalesced pending predicate 并只记录 wake，重复初始化或失败后重试返回稳定的 PAL state error。

预编译 Stack 会同步调用全局 `appm_init()`。该 ABI 由 `sdk_runtime` 提供，但实际 application initialization 通过 config callback 委托给 launcher。Component 不创建 `TASK_APP`，也不发送 `GAPM_RESET_CMD`。

预编译 Stack 通过 `rom_env.stack_printf`、selected RWIP source 通过全局 `uart_printf()` 进入同一个 `sdk_runtime` 静默 sink。该强符号只有 `sdk_runtime` 可以定义，不属于 public config，也不能由 image 使用 weak symbol 覆盖。Launcher 和 Board 的诊断统一调用 owner-prefixed bounded writer；深层日志不能触发格式化、UART I/O、allocation 或 application callback。

PAL Log 使用一个 `512`-byte component-owned ring，并把 level、scope、message 和行尾按 segment 直接写入 ring，不保留第二个 image-lifetime format buffer。单条格式化结果最多 `319` bytes；超限返回 truncated，同时仍以换行结束。该机制和容量属于可复用 BK3633 component，UART drain cadence 与启动诊断仍由 image/Board 组装。

只消费 selected RWIP source、但不启动完整 SDK application lifecycle 的诊断 image，
可以选择 `//native_component_src/bk3633/sdk_runtime:rwip_abi` source-set。该 target
仍编译 `sdk_runtime` 拥有的同一份静默 `uart_printf()` 实现，不建立第二个 public
contract 或符号 owner；完整 production image 继续选择 canonical `:sdk_runtime`。

## Core PAL

BK3633 没有 IP network stack，继续绑定 canonical
`h2_pal_unsupported_netif_api()`。System Event taxonomy 可以接受
`NETIF_DEFAULT_CHANGED` 订阅，但该 target 不伪造 Netif event；这与 BK7258 CP
一样是明确的 execution-unit exclusion，不是遗漏的 provider。

BK3633 是单线程 cooperative runtime。Image 创建一个 `libs/pal/providers/libco` executor，并把它提供的既有 PAL Task、Time、Queue 和 Sync API 注入 Runtime；finite/forever wait、close/reset generation、timeout 和 cancellation 都由 library backend 实现，不在 PAL 增加 target-specific wait/wake contract。

`//libs/pal/providers/libco:libco` 由 BK3633 ARMv5TE Thumb toolchain 独立编译成非 LTO `.a`。三个 `bk3633_firmware` action 都把该 archive 作为显式 input 传给共享 native Make；Make 不再枚举 wrapper 或 upstream libco source，只在最终 ELF link 的 object 列表之后消费 archive。这样 production、Log 和 Libco Smoke 共享相同链接机械且不会产生第二份 libco objects。Log image 只创建 executor 以取得 Runtime 必需的 Queue API，不启动 libco task 或 scheduler。

BK3633 Memory provider 由 `h2_pal_core` 唯一实现。每个 image 必须在首次 allocation
之前，由 Board 根据 linker `end`、保留 stack 边界和 board profile 计算可用 RAM，并通过
一次性 component config 注入这段 image-lifetime storage。Board 不能重新定义
`h2_bk3633_platform_mem_api()`，firmware graph 也不能通过排除 Memory source 的同名
component variant 替换 provider。Component 返回纯统计快照；是否以及如何输出容量、失败
请求和 fragmentation 属于 Board 或 launcher 诊断策略。

Runtime、WolfCrypt、FM17660K 和 NFC Type 2 的 semantic archive target 直接位于各自 `libs/**` owner package。BK3633 firmware graph 依赖这些 target，不为它们建立无源码的 `native_component_src/bk3633/h2_runtime`、`h2_wolfcrypt` 或 `h2_nfc` 包装 package；`native_component_src/bk3633` 只保留 SDK runtime、PAL backend 和其他确实由原生构建消费的源码与构建契约。

`//libs/pal:unsupported` 也由相同 BK3633 toolchain 编译成独立 archive。三个 firmware
action 从各自真实 Bazel graph 自动收集 `h2_libco` 与 `h2_pal`；共享
Make 不枚举 `libs/pal/src/unsupported/*.c`，并按语义 archive 分别链接。缺失
任一声明的 archive 都必须在 SDK probe 阶段失败，不能回退到源码编译。

Production image 的 `//libs/pal/providers/wolfssl:wolfcrypt_bk3633` 也由 Bazel 编译。其 BUILD
target 按既有合同拆分 ARM/Thumb 与 LTO/non-LTO translation units，并把 Crypto PAL
bridge、RNG bridge 和 upstream WolfCrypt closure 作为独立 cacheable archive action。
Native Make 不再枚举 WolfCrypt source；它只校验并以 linker group 消费 Bazel archive
closure，同时继续拥有 wrapper redirects、required/unused symbol、最终 LTO stack、
layout、Stack/BIM 和 firmware link 检查。

Tapdoki image root 创建 BLE Stack task 与 BK App task，并为同步 NFC card-emulation provider 创建一个 image-private worker；Runtime 初始化后再由既有 PAL Task provider 创建 Runtime input task。四个 task 的 image-selected stack budget 分别为 BLE Stack `1280` bytes、BK App `3584` bytes、Runtime input `1536` bytes 和 NFC worker `1024` bytes；Board allocator 为每个 stack 保留并检查 guard。NFC worker 只把 product App 提交的 bounded managed-profile request 复制到 image-owned storage，在自己的 libco context 调用 Board 已组装的同步 provider，并把完成结果交回 App；它不改变 PAL contract、FM17660K provider 或 Board frontend ownership。生产 root 只调用 bounded `h2_libco_schedule()` 并观察 BLE 与 App 两个 image-owned session handle 的终态；raw `rwip_schedule()`、copied-event dispatch 与 still-pending yield 都属于 BLE Stack task。IRQ 或 RWIP deep callback 只能复制 bounded state 和记录 wake，绝不能直接切换 context 或执行 App。

Image 在绑定 executor 时注入 Memory API 并选择 completion capacity，component 不提供固定值或 fallback。TapDoki 以 BLE Stack、BK App、Runtime input 与 NFC worker 四个可能同时等待 target completion 的 task 为上限，选择 capacity `4`；每个 task 同一时刻只允许等待一个 owner-defined key。Capacity 统计处于 `PENDING` 或 `DELIVERED` 的不同 key，和每轮 root dispatch budget 相互独立。

Completion bridge 从第一次记录 key 到对应 task 真正恢复期间合并重复 wake：root 只把 `PENDING` key 交给一个 waiter，成功后保持 `DELIVERED`，由恢复的 wait 调用确认并释放。真实 predicate 和 payload 始终由 RWIP、BLE、ADC 或 NFC owner 保存并在恢复后重新检查；queue 只表达需要检查 owner state。没有 waiter 的 stale key 在 root dispatch 时释放。Capacity full 保留已有 key，把错误暴露给 root 一次后允许 bridge 继续推进；production 把 full 视为 image capacity 配置错误并进入现有 scheduler fail-stop，不允许静默丢失 wake 后继续运行。

### GPIO Button 与 Buzzer

`h2_pal_core` 的 GPIO Button provider 在调用方上下文采样，分别保存每个 button 的候选状态和 press/release debounce deadline。采样回到已确认电平会取消候选；GPIO 或 monotonic time 失败不会推进状态。Provider 不创建 task、timer 或 Runtime event，Runtime 只消费已经稳定的 PAL reading 并生成客观 phased action；gesture 由 App 判断。

Buzzer provider 使用两个由 Board 注入的 PWM channel：一个生成连续频率，一个表达逻辑音量。Board 为每个 channel 选择 SDK counter continuous mode，Component 不硬编码这一项目策略。Provider 在初始化时只配置一次两个 PWM channel，后续 `start`、`stop` 和 cleanup 只更新 period/duty 寄存器。Component 校验 block/channel/GPIO 对应关系、频率范围和 `0..100` 音量，协调 partial failure rollback，并让重复 `stop` 和 cleanup 始终留下两个 channel 静音。Board 负责 volume polarity；portable PAL 和 App 始终把 `0%` 解释为静音。音符、时长、优先级和 melody 只存在于 App。

Tapdoki 保留 H300 的 Timer0 产品通道归属：channel 0 属于按键时基，channel 1 属于 RGB 刷新，channel 2 属于蜂鸣器时基。Board 使用 channel 0 每 `2 ms` 采样两个实体按键，并把稳定 DOWN/UP 边沿保存在有界队列；Runtime input task 只读取这些已经稳定的 PAL reading，不拥有该硬件时基。Stage 5 的 Board Timer PAL 安装一个固定 `5 ms` repeating timer 到 channel 1；Stage 6 再安装一个可变周期 one-shot timer 到 channel 2，在 callback 中推进已准入的旋律，不执行 allocation、Preference、event publication 或日志。App 仍拥有颜色、效果、提示音优先级、音符向量、长按判定和持久化状态。libco idle wake 不得占用这些产品通道，Tapdoki Board 将它放在 Timer1 channel 2。

### Time、Battery 与 Power

BK3633 Time provider 使用 RWIP half-microsecond counter 提供 monotonic time，并通过 Board 注入的 portable BM8563 driver transport 提供 wall clock。Tapdoki Board-owned executor time callback 在 `rwip_init()` 完成前固定返回零；launcher 的 SDK-started callback 只通知 Board 打开该 time source，Runtime library 不拥有这一 target 启动时序。Driver 对地址 `0x51` 执行一次 coherent 7-byte read，验证 voltage-low、BCD、calendar 与 century，支持 1970..2099；set 在 STOP 保护下完成写入和 readback，失败时 best-effort 恢复控制状态。TapDoki Board 使用 P02/P03 I2C 与 P07 active-low pull-up interrupt；这些 wiring 不进入 component contract。

Battery provider 在调用方 task 内发起 ADC conversion，并通过 libco wait 等待包装后的真实 ADC ISR 记录 completion wake；对外只返回 fresh/cached sample、timeout、cancellation 或错误，不要求调用方用相同参数推进。它拥有单个 ADC transaction，按固定 interval 采样并使用 Board 配置的 raw endpoints 做饱和线性映射；首次 charging/full GPIO 采样立即建立稳定状态，后续边沿使用 Board 配置的 debounce；放电时 percent 不上升，进入 charging 后重置该 clamp。SDK flash 低压检查会临时占用并重配 ADC，最终 firmware link 必须把它和 ADC ISR 路由到 component-owned wrapper；wrapper 在检查返回后恢复 Board 注入的 Battery ADC 配置，并在抢占 conversion 时唤醒原 task重新采样。Board 不实现 ADC 仲裁或 SDK wrapper。TapDoki Board 配置 P32 ADC channel 2/mode 1、raw `161..195`、P33 active-low charging、P22 active-low complete 和 `2000 ms` interval。

Power provider 只暴露 reboot、sleep、deep sleep、boot source 与 reset reason，不声明 hold 或 shutdown。Advertising standby 先要求 RWIP 可睡，再执行 CPU voltage sleep/wake；deep sleep 只在 Board 验证 P04 已稳定释放后配置 falling-edge wake。TapDoki Board 在低功耗前停止 input acquisition、关闭 RTC bus、关闭 shared rail P10，并 park P02/P03/P06/P11/P13/P16/P17/P32；wake 后按相反顺序恢复。产品的启动门、activity、standby eligibility 和 transition reason 仍由 portable App 拥有。

## FM17660K NFC

Portable FM17660K driver 只接收 exact `write_reg/write_regs/read_reg/read_regs`、fallible sleep 和 reset。它拥有 FIFO data-register 使用、UART byte-command encoding/read flag/echo validation、reader/card protocol state 与同步 card-emulation window；public transport 不暴露 UART、FIFO callback、partial progress 或 caller replay contract。

具体 UART2、reset pin、共享供电、IRQ ring 和 readiness wait 属于 Tapdoki Board。Board 把 exact-byte endpoint 注入 portable constructor；UART2 wrapper 自己处理 RX/TX/error status、记录 wake，且不进入 vendor download-command parser。每次 exact operation 使用单一 absolute deadline，timeout/cancellation 关闭 interrupt mask 并执行确定性 drain/recovery。

## BLE Host

BK3633 BLE backend 实现现有 `h2_pal_ble_host_api_t`。SDK message 只在 dispatcher 期间借用；需要跨调度投递的 payload 必须复制到 component-owned bounded storage。

事件路径为：

```text
PAL operation
    -> RWIP command
    -> rwip_schedule()
    -> launcher TASK_APP default handler
    -> component BLE dispatcher
    -> copied pending system event
    -> rwip_schedule() returns
    -> Runtime event dispatch
```

Runtime callback、application callback、blocking queue、allocation 和深层 logging 不能从 IRQ、FIQ 或 RWIP scheduler 深栈调用。连接、断开、广播状态等 lifecycle event 必须无损复制；其 pending queue full、oversized payload 和 dispatch failure 必须返回明确错误，launcher 不能忽略。Passive scan report 是允许丢包的观测流：component 只保留 bounded 最新窗口，突发填满窗口时覆盖最旧报告，不能把正常 RF 密度转成 SDK Runtime fatal。

Provider 根据编译期 Stack capability 实现 operation；当前 Stack 不支持的 operation 使用完整 vtable entry 返回 `H2_PAL_ERR_UNSUPPORTED`。Tapdoki 只选择 allroles Stack contract。

BK3633 provider 支持 legacy connectable advertising set 的独立 scan-response data。Provider 分别复制并编码 primary 和 scan-response AD structures，后者不插入 Flags，并按 `GAPM_SET_ADV_DATA`、`GAPM_SET_SCAN_RSP_DATA`、activity start 的 completion 顺序串行提交。当前 component 不把该 operation 扩展到 Extended Advertising；App 继续拥有 service UUID、local name 和 manufacturer data 的内容与分包策略。

BK3633 component 串行化 indication；`h2_pal_ble_indicate()` 保存 private outstanding connection、attribute、SDK sequence、generation 和 terminal result，并通过 libco wait 等待匹配 `GATTC_CMP_EVT`、disconnect、Host stop 或 absolute timeout。返回值直接表达 peer confirmation/failure；迟到 SDK completion 只释放 abandoned private state，不能完成更新一代调用，也不产生 PAL/Runtime completion event。

Inbound GATT read/write request 使用 component-owned bounded queue 保存完整请求副本，不能像 passive scan report 一样覆盖旧请求。Board 在 `h2_bk3633_platform_ble_config_t` 中注入 Memory PAL 并选择 queue capacity；component 在 image lifetime 内只 configure 一次，借用 Memory/Time PAL，并按该容量分配 storage。容量为零、配置重复、整数溢出或 allocation failure 都返回明确错误。Queue full 对当前 ATT request 返回资源不足，不丢弃或覆盖已经排队的请求。Capacity 是 image 的 target resource composition，不进入 portable App 或 Runtime event capacity。

## Persistent storage 和 Crypto 组装

`h2_pal_core` 中的 storage provider 只接受 application-owned NVDS tag mapping 和 BSP 声明的 Flash partition。NVDS provider 不重置或擦除 SDK storage，不修改 RWIP hook；Disk provider 不允许 portable caller 访问 absolute Flash address。SDK Runtime 仍唯一拥有 `flash_init()` 和 `nvds_init()`；两个 provider 只能在 `h2_bk3633_sdk_runtime_platform_init()` 完成 Flash/NVDS 初始化后进入 ready 状态，不能从 IRQ、FIQ 或 RWIP scheduler deep callback 调用。

Canonical `sdk_runtime` 使用 component-owned extended NVDS ABI 取代 pinned SDK 的
512-byte browse 上限，并拥有 record walk、compact、maintenance 与全部 `nvds_*`
全局符号；选择 minimal `:rwip_abi` 的诊断 image 可以继续使用 SDK 实现。Board 只
注入 application tag mapping，以及旧 schema 的 oversized value 是否按 missing 处理的
迁移 policy，不能定义或替换 `nvds_*` ABI。

TapDoki v2.0 的 board config 声明 8 KiB record partition，其后保留一个 4 KiB guard sector，再接 NVDS。BK3633 SDK 在 `flash_init()` 中读取 JEDEC capacity code，并为 512 KiB 或 1 MiB Flash 设置 `flash_env.nvds_def_addr_abs` 与 BDADDR sector；board storage 必须从这个已探测地址推导实际 partition base，不能把构建期容量当作运行期检测结果。配置中的 4 KiB NVDS reserve 表示 SDK NVDS 所在的末尾擦除扇区，不等同于 NVDS tag store 的逻辑可用字节数。Linker 以 512 KiB 支持下的最早 record 地址作为 image 上限，因此同一 image 对两种容量都安全；Runtime 再校验实际地址、sector 关系和 image load end。Tapdoki allroles image 必须发布完整的受支持布局集合。该 partition 只表示 capacity，不定义 record、CRC、journal、ring 或 domain schema。

BK3633 entropy adapter enable hardware TRNG，并以 bounded poll 填满同步请求。连续 32-bit word 重复、timeout 或 read failure 都返回错误并清空 caller output，不回退到 `rand()`、BLE controller random、device address、timestamp 或其他 predictable source。BSP 在 Runtime assembly 中先执行一次 entropy health check，再直接调用 `h2_wolfcrypt_crypto_init()` 并消费 `h2_wolfcrypt_crypto_api()`；singleton lifecycle 和 ready 状态属于 `libs/pal/providers/wolfssl`。Required provider 失败时 board Runtime assembly 反向清理已经 ready 的 storage capability。

## Allroles image inputs

Tapdoki production project 的 native configuration 成套选择 allroles Stack/BIM/OAD、`rwip_config.h`、`rwprf_config.h`、`user_config.h`、兼容 linker layout 和 compile-time configuration：`CFG_ROLE=4`、`CFG_CON=1`、`CFG_ACT=4`。产品只保留一个 peripheral connection；两个 advertising set 与 passive scan 同时占用三个 activity，并保留一个 activity 给 stop/restart transition。Board 只提供物理 linker layout 文件和 Flash/RAM 约束，不默认注入这个 project policy。Allroles linker 把 SDK 的 named `ke_heap` 收进 startup-cleared `NOLOAD` BSS，再在其后定义 Board Memory arena 使用的 `end`；该 RWIP static storage 不能被当作 App heap 重用。

Launcher 从同一个 `BK3633_PATH/SDK` 取得 `src/system/BK3633_STACK_ALLROLES.elf` 和 `projects/app_gatt_all_roles/output/stack/BK3633_STACK_ALLROLES.bin`。Stack ELF 只作为 linker `--just-symbols` input，Stack BIN 参与 merge。BIM 直接使用同一 repo 的 `SDK/projects/boot_for_all_roles` source、linker 和 Makefile，不能复制到 GizOS 或回退到 committed binary。

## Log diagnostic entry

`projects/tapdoki/targets/bk3633_firmware/log/tapdoki_v2_0` 是更小的 full-image 诊断入口。它在 UART 初始化后、GPIO 与 Runtime 初始化前直接输出一次 `H2_BK3633_LOG_UART_READY`，再初始化 TapDoki GPIO、PAL Log 与最小 Runtime，循环调用 portable `log` App 并 drain 每条日志；不启动 RWIP、不进入 production App，也不启动 libco task 或 scheduler。Log root 仅创建 executor 以复用 library-owned Queue provider，不在 launcher 中重复一份 queue backend。随后在 115200 baud 持续输出的 `[I][log] Hello World` 才验证 Runtime Log；两类输出共同把 boot/UART/Runtime Log 问题与 Libco Smoke 执行问题分开，不能替代后者验收。

## Libco Smoke diagnostic entry

`projects/e2e/targets/bk3633_firmware/libco-smoke/tapdoki_v2_0` 与 production `main`
是两个独立的 full-image entry。两者分别拥有显式 native configuration，并选择兼容的 allroles SDK、Board linker layout、BIM、Stack、
BinConvert 和 release checks；diagnostic entry 不链接 TapDoki production App，
但复用 Board target executor、`h2_bk3633_platform_libco_bind()` completion bridge
和 BLE Stack task 来推进 RWIP。

Target executor 和 portable smoke 的独立 executor 都固定在 SDK boot/main root
context，使用 upstream ARMv5 backend。诊断 BLE Stack task 使用 1280-byte stack；portable
smoke 从 component Memory provider 上由 Board linker RAM 区域配置的同一个 arena，为最多
三个 coroutine 分别显式分配 2 KiB stack，并运行 10,000 次 cooperative switch。Launcher-owned Time wrapper
只在所有 smoke coroutine 已返回 root 后执行 bounded wait，同时允许 target
executor 推进 pending RWIP work 并 drain log；smoke coroutine entry 不调用 SDK、
Runtime I/O、sleep 或 allocator。

BK3633 runner 的 maintained entry contract 同时包含 TapDoki production `main`、`log` 和 Example-owned `libco-smoke`，并逐个校验独立 ELF、BIN、map、manifest 和 merge CRC image。这项构建验证不能替代各入口使用文档要求的 TapDoki 真机下载、冷启动 marker 和 fault/reset 检查；Log Example 要求持续 PAL Log，Libco Smoke 要求两次完整冷启动且每次都连续观察至少三次 `READY` 心跳。USB-UART 随板卡掉电时，host monitor 必须在端口重新枚举后自动重连。

完整 firmware build 需要先激活共享 provider environment，再构建 canonical label：

```sh
. ../firmwares-devenv/export.sh
bazel build --config=bk3633  //projects/tapdoki/targets/bk3633_firmware/main/tapdoki_v2_0:firmware
```

仓库级 `make bazel-build BAZEL_CONFIG=bk3633` 和 GitHub Actions 的 `bk3633` execution class
构建完整 configured `bk3633_firmware` graph，并执行同一套 SDK identity、toolchain specs、probe、link、stack 与 release
artifact 验证；CI 使用只读 deploy key checkout firmware-devenv 锁定的 BK3633
SDK commit。它只证明固件能够构建，不能替代 Tapdoki 真机启动和 BLE/NFC 验收。

每个 Bazel target 必须在自己的 `firmware/` output directory 生成 `firmware.elf`、`app.bin`、`firmware.map`、`merge-crc.bin` 和 canonical `manifest.json`；只有 `merge-crc.bin` 是整机烧录输入，不生成 H2Loader package。真实硬件验证还需要覆盖广播、连接、GATT read/write、CCCD notification/indication、断开重连、scan/Extended Advertising，以及至少 30 分钟无复位和 stack guard fault 的持续运行。
