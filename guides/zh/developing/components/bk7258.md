# BK7258 Components

BK7258 包含 AP 和 CP 两个 firmware side。它们拥有不同的 SDK capability、启动流程、link boundary 和运行职责，因此 Components 必须按执行单元拆分。

## Task policy ownership

AP 与 CP 的 `h2_pal_core` 只负责一次性配置、policy 校验、Beken task 创建、诊断、join 和清理；共享 provider 不得比较具体 App、library、Loader、packaging workflow 或产品 task name。最终 name、priority、core（仅 AP）、minimum stack 和 Default/PSRAM placement 由每个具体 firmware target 的 `task_policy/<ap|cp>/h2_bk_target_task_policy.c` 自包含地决定。AP target 直接声明自己的 trie routes，并在 trie 上注册 name-aware 默认 handler；没有特殊 route 的 CP target 由单一 name-aware resolver 直接返回默认 policy。两者都不通过共享 route table、PAL fallback 或通用字符串比较层转发。

Launcher 必须在 board Runtime configuration 或 CP startup task 之前调用 `h2_bk_target_task_policy_install()`。配置只能成功一次，未配置启动、重复配置和 task start 后配置均返回 `H2_PAL_ERR_INVALID_STATE`。AP target 可通过 `h2_trie_set_fallback()` 注册与普通 route 相同签名的默认 handler；trie 未命中时把完整 task name 放在 `match.path` 传给该函数，由 target 动态决定 SDK name、priority、core、minimum stack 和 stack placement。Public targets 的默认逻辑在 AP 返回 pass-through name、core 0、priority 7、4096 bytes、Default stack，并用 PSRAM allocator 分配 PAL task handle；CP 返回 pass-through name、priority 6、4096 bytes、Default stack。Private target 可不注册 AP 默认 handler，或让 AP handler / CP resolver 返回 `H2_PAL_ERR_NOT_FOUND` 来拒绝，并显式传入 `ap_task_policy` 与 `cp_task_policy`。

Public AP targets 保留它们共同需要的 H2Loader command routes。App-specific routes 不再由 board layout 泛化注入：audio routes 只出现在 audio-system target，`bleikcp-speed/` prefix 只出现在 BLEIKCP speed client/server targets。旧 provider 内的 `cmd/h2test`、`cmd/apploader`、`ble_speed_p/c`、`h2peer/net/udp`、`mfg-music/mic` 与所有 CP special cases 已移除；仍依赖它们的 downstream image 必须在自己的 private target 中声明。

## 目录结构

```text
native_component_src/bk7258/
├── ap/
│   ├── h2_pal_core/
│   ├── h2_bk_audio_decoder/
│   ├── h2_gizclaw/
│   ├── opus_port/
│   └── zlib/
└── cp/
    ├── h2_pal_core/
    └── h2_cp_transport/
```

AP-only component 不能链接进 CP。CP-only UART、shell、mailbox 和 transport helper 也不能隐藏在 AP component 中。

Bazel archive 的薄 Armino adapter 统一位于 `native_component_src/bk7258/ap/<component>/`。它们不是第二份 library 或顶层 SDK implementation component，只负责 AP registration、include propagation 和 archive import；共享 archive import helper 位于 `native_component_src/bk7258/ap/cmake/`。

## AP Ownership

AP Netif provider 在 lwIP tcpip context 中复制 `netif_list`/`netif_default` 快照，
并映射稳定 index、kind、IPv4、MTU、MAC 和默认 resolver。Wi-Fi STA/AP 可由
Armino handle 识别，board-owned PPP 在创建/释放时通过 AP-only registration
hook 登记 identity。

Wi-Fi IPv4 获取/丢失与 Zero PPP promotion/restore/teardown 在 route 已提交后
reconcile。SDK/lwIP callback 只向现有 AP system-event worker 投递内部 reconcile
请求；worker 再通过 `tcpip_api_call()` 捕获快照、推进 baseline 并发布正式事件，
避免 TCPIP thread 自等待，也不在 lwIP critical section 内调用 Runtime。post
failure 不回滚 route。CP 不拥有 AP 网络栈且不运行 App Runtime，所以不实现
Netif provider。

AP 是 BK7258 app Runtime 和 H2Loader Runtime 的 owner。Display、audio、LVGL、bundle install、network integration 和 app-facing Runtime 运行在 AP。

`native_component_src/bk7258/ap/h2_pal_core` 提供 AP 所需的 PAL backend，包括 mem、log、
sync、network、netif、task、queue、time、crypto、DTLS、preference、system event、
Wi-Fi、BLE，以及按 build capability 选择的 MQTT 和 WebRTC backend。它编译
portable `libs/pal/providers/corehttp` 作为 SDK build adapter，但不拥有 BK HTTP client 或 HTTP
accessor。WebRTC 直接构造 `libs/pal/providers/h2peer` 并注入这些 PAL capability；BK 不维护
H2Peer 或 libpeer 专用 port component。

AP Net backend 使用 bounded asynchronous resolver thread 实现 Net PAL 的
`resolve_start`/`resolve_poll`/`resolve_close`，使 portable consumer 的总 deadline
同时约束 DNS、connect、TLS 和 HTTP I/O；resolver capacity 用尽时返回
`H2_PAL_ERR_NO_SPACE`，close 不等待 worker，并由 backend 回收迟到结果。TLS 使用
SDK public Mbed TLS 实现现有 `tls_wrap`，wrapped socket 的 send、bounded send、
recv 和 close 保持同一个 PAL socket id。BK 没有可依赖的 production system CA
bundle：`REQUIRED` HTTPS 必须提供显式 root CA，否则返回
`H2_PAL_ERR_UNAVAILABLE` 并 fail closed；禁止使用 SDK test CA 或静默切到
`VERIFY_NONE`。BK CP 不拥有 network/HTTP provider，也不编译 coreHTTP、llhttp 或
TLS client code。

AP component 可以复用 Libraries 和 third-party integration，但 board GPIO、partition、storage layout 和 runtime config 由 BSP 与具体 image entry 提供。

BK7258 `libco-smoke` launcher 从 `projects/e2e/apps/libco` 编译 portable App。Bazel 用 BK7258 Cortex-M33 hard-float/CMSE platform toolchain 把 wrapper 与 `third_party/libco_patch/backends/cortex_m.c` 归档成唯一的 `//libs/pal/providers/libco:libco`；`native_component_src/bk7258/ap/h2_libco` component 声明 archive 和 native component name，firmware rule 沿 component dependency graph 把它作为原生 action input 交给 AP CMake imported target，Armino 不再重复编译 libco source。Backend source 自身继续用 Thumb、M-profile 和 32-bit compile-time guards fail closed，避免执行 upstream `arm.c` 的 A32 instruction words，并按 AAPCS 保存 callee-saved core 和可用的 floating-point registers。Armv8-M 的 `PSPLIM` 与 `PRIMASK` 也必须随 context 保存；backend 在关中断窗口内清除旧 limit、切换 SP、恢复新 limit，不能让 FreeRTOS AP task 的 hardware stack limit 作用于 heap-backed coroutine stack。这个 library 只链接进 AP image，不进入 CP。一个 executor 只能在 Board-owned AP entry task 内创建和调度；每个 coroutine 仍由调用方分配独立固定 stack，handle 不得跨 AP task、IRQ、callback 或 CP mailbox。Image 保留 board-standard AP/CP Bluetooth controller、IPC 与 reliable command transport，不能通过关闭 AP auto-enable 或 CP Bluetooth 拆开双核启动契约；CP 不链接 libco。

## Bazel External Build

BK7258 的原生 AP/CP、partition 与 linker 语义继续由 Armino SDK 和 launcher CMake project 拥有。全部 17 个 maintained BK7258 launcher 都有内部 `bk7258_firmware` external build target；Bazel 负责统一入口、结构化 native 输出与 Loader recovery publication，不复制 SDK 编译语义。

`bk7258_firmware` 必须使用显式 `bk7258` platform。`BK7258_PATH` 只进入 SDK repository evaluation；native action接收已验证SDK locator、Bazel下载并双重校验的Arm GNU 10.3-2021.10 locator、可选ccache runtime locator与固定subprocess environment，不继承caller path。Action将launcher和build tree放入invocation-local临时目录，只以内部`H2_REPO_ROOT`读取原仓库，直接调用SDK `make`；发布outputs前重新验证SDK commit与tracked cleanliness，并确认GizOS checkout未被native build修改。不得调用launcher Makefile或CI wrapper；native outputs与Loader recovery由该Bazel action声明生成，package和metadata由下游`h2loader_tar_zlib` action生成，两者都不执行flash、reset或设备流程。

显式提供 native ccache 时，runner 在验证原始 ARM toolchain identity 后，通过 Armino 的 `ARMINO_CCACHE_ENABLE` 与 CMake `RULE_LAUNCH_COMPILE` 接入 ccache。所有 BK7258 launcher 共享 `bk7258` cache namespace，并使用 GCS `ccache/bk` family prefix；AP/CP source、config、compiler flags 与 generated header 是否命中由 ccache compile key 判定。该 prefix 与 ESP `ccache/esp`、Bazel `firmwares` 分离。cache 不能修改 SDK checkout、替代 AP/CP build graph，或绕过 build 前后的 identity 与 cleanliness validation。

每个 graph component 必须声明 `execution_unit = "ap"` 或 `"cp"`。Runner 只把该 graph 可达的 component 文件复制到 action-local、以 component name 命名的 AP/CP staging tree，并生成两侧独立的 component directory 和 direct-source manifest。Top-level CMake 只注册当前 `ARMINO_SOC` 对应的一侧；component CMake 通过统一 helper 读取自己的 source list。不得从仓库扫描 component、保留 launcher source fallback，或让 AP source 进入 CP。

结构化产物保持 AP/CP ownership：AP 与 CP 各自提供 ELF、map、app image，另行提供 managed `app_ab_crc.rbl`、recovery `all-app.bin` 与固定 partition metadata directory；Loader role 再提供 `.recovery.h2fb`。平台无关的 `h2loader_tar_zlib` 消费 managed image 与具名 native artifact，提供唯一的 H2Loader package 和 `.firmware.json`。所有 artifact 都必须在本次 build root 内解析并通过非空或 JSON object 验证，不能把整个 SDK output tree 或混合 AP/CP 的不透明目录作为 public provider。

AP 的 EtherMind GATT server 从 `BK_GATTS_CONNECT_EVT` 取得 server-side connection ID；不能用 GAP `link_role` 过滤该连接，也不能把 server GATT ID 传给仅接受 central connection 的 update、MTU 或 PHY API。直接收到的 CCCD write event 是 subscription 的 authoritative state，value write callback 不得重入 `bk_ble_gatts_get_attr_value()`。Notification 在 `bk_ble_gatts_send_indicate(..., false)` 被 controller 接受后完成，因为 SDK 不会为 notification 发送 `BK_GATTS_CONF_EVT`；只有 indication 使用 `BK_GATTS_CONF_EVT` 完成同步 `h2_pal_ble_indicate()`。由于 SDK confirmation 不提供可依赖的 attribute handle，provider 只串行化 indication；冲突 indication 返回 `H2_PAL_ERR_BUSY`。Provider 用 private generation/result 等待 confirmation、disconnect、Host stop 或 timeout；迟到 confirmation 只能释放 abandoned state，不能匹配后续调用。Legacy BLE stack 无法可靠观察 peer confirmation，因此在发送 indication 前返回 `H2_PAL_ERR_UNSUPPORTED`。CP 不拥有 BLE Runtime 或这项能力。

AP BLE Host 的 EtherMind 和 legacy build variant 都显式接入可选的独立 legacy scan-response operation，但当前返回 `H2_PAL_ERR_UNSUPPORTED`。既有 primary advertising encoder 对 local name 的内部拆分不构成独立 PAL capability；在补齐两种 Stack 的 lifecycle、clear、failure 和固件验证前不能报告支持。CP 不拥有 BLE Host vtable，因此不需要适配。

AP Crypto provider 使用 BK SDK 的 public PSA/MbedTLS capability 实现完整
Crypto PAL，包括 X25519、AES-CTR、MD5 和 HMAC-SHA1。它不维护本地 X25519
ladder，不 include SDK private crypto header；注入 portable library 后的 key、
nonce、counter、overlap 和错误语义与 Desktop/ESP provider 相同。
`h2_pal_core` 在 SDK-owned `psa_mbedtls` component 上启用这些 public capability，
不直接复制或编译 SDK crypto source；因此所有 BK launcher 只链接一份实现。

通用 task backend 只提供 target-level 的 policy hook 和少量与产品无关的默认 policy。具体 image 负责注册完整的 task name、core、priority、stack size 和 stack memory region；严格模式下，未登记 task 必须返回错误，不能静默使用默认 core 或 internal stack。Image 的 task table 和 memory budget 应由 machine-readable contract 在编译前校验，避免产品 task 名称进入 reusable BK component。

BK7258 默认 AP Runtime config 仍把 Video Decoder 和 Audio Decoder 绑定到 canonical unsupported backend。需要 MP4 playback 的 image 显式链接 `h2_tinyh264` 与 `h2_bk_audio_decoder`，并只在该 image 的 launcher config 中覆盖两个 provider。`h2_tinyh264` 返回 CPU-readable decoded frame；`h2_bk_audio_decoder` 使用 SDK Helix AAC decoder 返回 S16LE PCM。其他 image 不能因为这些可选 component 存在就报告 decoder capability。

`h2_game_audio`、`h2_game_runtime`、`h2_pixa` 和 `h2_yyjson` 是可选 adapter；只有实际使用对应 library 的 AP image 才显式依赖它们。PIXA Games 不创建逐游戏 AP component wrapper；image AP component 使用 `projects/pixa_games/libs/cmake/pixa_game.cmake` 编译 project-owned game library。`h2_yyjson` 只在 AP 编译 `libs/pal/providers/yyjson` 和 pinned upstream，CP 不注册、链接或选择这个 provider。

H2Loader-only BK AP adapter 位于 `projects/h2loader/native_component_src/bk7258/ap/h2loader_bk/`，由 BK H2Loader launcher 消费；它不属于仓库级 BK component。为适配 display layout 的 AP heap，Loader/App BLE-iKCP session 固定使用 8 KiB TX buffer、8 KiB RX buffer 和 16 个 inbound frame slot；协议、MTU 与 command contract 不变，disconnect 会释放整个 session。Loader 与默认 App management service 都强制使用 legacy advertising，primary packet 保留 private service UUID，compact Loader identity 放入 manufacturer data；独立 scan response 可以承载 identity，但 Host 不能依赖 CoreBluetooth 必然合并它。两端的无响应 BLE write 对 `WOULD_BLOCK` 使用 40 次、每次 2 ms 的 bounded retry，耗尽后仍返回 transport error。

## CP Ownership

CP 负责自己的执行环境和辅助职责。CP Components 包括：

- `h2_pal_core`：提供 CP 实际需要的 mem、log、sync、task、queue 和 time 等基础 PAL capability。
- `h2_cp_transport`：独占 UART0 RX，把任意 binary byte stream 有序传给 AP，并重组 AP 通过 private transaction envelope 提交的完整 protocol frame。CP 只处理 tunnel 的 begin/data/end、sequence、length 和 lifecycle，不解析 H2IKCP 或 H2Loader command。

CP 不运行 app Runtime，因此不需要提供 AP 的完整 PAL surface，也不创建第二套 Runtime config。CP 与 AP 的交互必须通过明确的 mailbox、transport 或 command contract，不能直接共享 AP object pointer。

所有 BK H2Loader package 共享 `projects/h2loader/native_component_src/bk7258/cp/h2loader_cp_launcher` 作为唯一 CP entrypoint；target 不复制 `cp_main.c`。launcher 在 `bk_init()` 前创建固定 1024-byte stack 的 `h2-cp-bootstrap`，等待 500 ms 后启动 transport。当前 transport start API 只有成功或失败结果，不区分 terminal error，因此 bootstrap 对任意非零结果每 100 ms 无限重试：`H2_BK_CP_BOOT` 表示重试阶段已经开始，只有成功后才输出 `H2_BK_CP_TRANSPORT_READY status=ready`、vote CP1 on 并退出。全芯片 reset 会终止尚未成功的 bootstrap；不提供独立 shutdown handshake。

BK H2Loader reliable UART 的数据路径是 Host UART0 → CP physical stream → mailbox tunnel → AP UART PAL → `h2_iostreamikcp` → Loader/App command owner。UART0 固定为 230400 8N1、no flow control；Host 默认值与固件一致，显式 `--baud` 只用于另行配置的镜像。Loader 与 App 必须使用同一速率，不在会话中途切换。CP 的唯一 RX owner 同时接收中断字节和 bounded short-frame polling，不能让两个 writer 并发写 ring。AP 的一次 PAL frame write 使用带 sequence 和 declared length 的 SLIP-framed begin/data/end transaction；CP 只在完整、有序 transaction 结束后暂停 shell TX、同步写出整个 frame，再恢复 shell TX，因此普通日志只能出现在 frame 前后。CP ready reply 与 sequence-tagged physical-TX completion ACK 由一个 mutex-protected control channel 和独立 pure tracker 分流，ready wait 不能消费 pending ACK，非匹配 sequence 也不能清除它；AP 的 PAL write 在收到匹配 sequence ACK 前不能报告成功。malformed、重复、越序、超长或 restart 中断的 transaction 必须整笔丢弃，fresh begin 可以恢复同步。Host 的 `SESSION_CLOSE` control frame 沿相同 tunnel 传给 AP，Loader/App 只停用对应 session；它不是 H2Loader command payload。

普通 managed connection 在 open 后、借出 stream 前将 DTR/RTS 置低；canonical `UNSUPPORTED` 表示 endpoint 没有可操作控制线并允许继续，其它错误立即失败。AP 从设备端 BLE public/identity MAC 导出 12 位小写十六进制 `device_uid`，Loader 与 App 的 UART/BLE status 必须一致。

H2Loader transport 的 12 KiB UART RX ring 和长期 transport task 必须使用 PSRAM，避免占用 CP internal RAM。Loader/app 在提交 `boot_intent`、三槽 metadata 或下次启动分区后使用 `bk_wdt_force_reboot()` 完成 AP/CP whole-device reset；final Host acknowledgement 丢失或 CP 仍占用 UART 都不能阻止已经提交的状态转换。BK command output 以包含换行符的完整 line 为原子 write，iostream 只在 line boundary flush。

generic BK shell 仍可输出日志，但所有启用 `h2_cp_transport` 的 CP image 必须关闭 `CONFIG_CLI` 与 `CONFIG_AT`，避免 SDK shell 或 AT task 在启动时重新注册 UART0 RX callback；这些 image 不让 shell CLI/AT parser 消费 UART0 输入，也不注册 raw H2Loader proxy。`h2_cp_transport` 对启用 CP CLI 或 AT input 的配置执行编译期拒绝。AP 与 CP 的 target-private deinit/stop 必须使阻塞操作返回 closed、清除未完成 transaction，并允许下一次初始化建立 fresh session。

## Armino Integration

BK component 使用 `armino_component_register()` 声明 source、include 和 AP/CP dependency。Component 可以依赖 Armino API，但跨平台 Library 和 app 不能 include Armino private header。

AP 的 `h2_audio_mixer`、`h2_bleikcp`、`h2_coremqtt`、`h2_iostreamikcp`、`h2_mp4_decoder`、`h2_pixa`、`h2_tinyh264`、`h2_utils` 和 `h2_yyjson` archive target 由消费它们的 firmware entry 直接拥有，对应 `libs/**` package 只定义普通 Bazel library。Firmware graph 收集 entry 显式列举的 semantic archive、public include closure 与 native component name，runner 在 action-local staging tree 生成 Armino registration；仓库不保留只传播 include 并导入 `.a` 的 AP component 目录。`lvgl_port` 因为仍拥有 BK Kconfig 和 native registration contract 而保留。静态 archive 只按最终链接中的真实未解析符号抽取 object，不使用全库 retention。该合同只作用于 AP；CP 仍由自己的 source/component graph 编译。

`//libs/pal/providers/libco` 与 `//libs/pal:unsupported` 由每个 BK7258 firmware entry 的唯一 `firmware_lib_component` 与其他 portable libraries 一起声明。AP `h2_pal_core` 只保留源码真正需要的普通 library 依赖；不再存在 `native_component_src/bk7258/ap/h2_libco` 或 `h2_pal` 目录。Armino source list 不重复编译 libco 或 `libs/pal/src/unsupported/*.c`。这些 archive 只属于声明它们的 AP firmware closure，CP 仍只编译实际实现和使用的 CP PAL component。

AP 与 CP 的 build registration 必须保持 side-specific：

- AP component 只声明 AP 可用 SDK dependency。
- CP component 只声明 CP 可用 SDK dependency。
- AP/CP 都需要的逻辑应先确认能够在两个执行环境安全运行，再分别接入 build；不能通过跨 side link 偷偷共享 binary state。

## BSP Boundary

BK BSP 位于 `boards/<board>/bk7258/`，负责：

- Board canonical `ap.defaults` 和 `cp.defaults`。
- Physical pin map 和 `usr_gpio_cfg.h`。
- Board partition data。
- Board hardware defaults。
- AP Runtime config 和实际 capability 组合。

BK 固件配置没有具名 config profile：`boards/<board>/bk7258/layouts/<layout>/` 下的每个 layout 自包含一组 AP 配置、CP 配置、GPIO 选择、`ram_regions.csv` 内存分布和 partition metadata，firmware target 只通过 `layout` 属性引用一个 layout；有效配置 = board canonical defaults 按序叠加该 layout 的 AP/CP defaults，Armino SDK 只提供 toolchain、Kconfig 定义、driver 和 component，不提供任何预置应用配置或 project template。Components 不拥有这些 board facts。AP/CP partition layout、H2Loader slot policy、SD `/dl`/`/data` mapping 和 command routing 也不属于通用 BK component。

## Validation

BK component 变更至少需要验证：

- AP 和 CP 分别能够编译。
- AP component 没有被 CP 链接。
- CP transport 没有进入 AP-only runtime dependency。
- AP Runtime config 只引用 AP 拥有并已初始化的 capability。
- AP/CP communication 使用明确的 transport contract。
- Image-specific memory contract 在 SDK 编译前和 link 后都通过，且 task policy 不依赖未检查的 default core、priority 或 internal stack fallback。

使用本地 Armino SDK、串口或硬件前，先读取 `.env/users/<os-user>.md`。SDK 和 toolchain 由同级 `../firmwares-devenv` checkout 统一提供，不使用个人 shell environment 文件；不能提交的 secret 只放在本机 `~/.config/h2loader/env`。
