# Upgrade erase failure propagation

The pinned SDK revision is `eb04f1966cf2b7cbb72cbb54db906bcb293b5a4a`. The [earlier IR audit](./pal-review-followup-sdk.md) establishes that `update.a` discards `dev_upgrade_erase`'s return. Native disassembly additionally shows `norflash_ioctl` returning `norflash_erase`'s result, while `norflash_erase` discards `norflash_wait_ok`'s result and returns zero after issuing an accepted erase. Its sizes are block 65,536, sector 4,096 and page 256 bytes, with the address rounded down to that size. A conventional callback-return change alone therefore cannot establish physical success. Emitted-code excerpts are `tmp/jieli/pal-review-next/o11/norflash-ioctl.dis` and `norflash-erase.dis`.

The adapter now checks ioctl and reads back every byte of the aligned erase range using the existing raw NOR API, in 256-byte stack chunks. Any ioctl error, short read or non-erased byte permanently latches failure for this boot. Subsequent adapter reads/writes, header arming/copy/publication and Loader write/finish/boot completion gates reject that failure. An SDK completion callback reporting success cannot overwrite the failure. No lock spans SDK calls or observers. Successful erase observers run only after verified erase.

The latch deliberately requires a new boot; a new write attempt cannot erase evidence while a late SDK callback may still be active. This follows the existing header gate's fail-closed lifetime and introduces no compatibility flag. Flash faults are not injected on hardware. Readback detects observed failures; it does not provide atomicity against power loss or a later physical flash fault.

`//tools/bazel:jieli_upgrade_io_test` compiles the actual adapter and Loader completion callback. Faults cover ioctl failure, a dirty last byte and short readback, followed by the SDK ignoring the result, attempting writes/publication and reporting successful completion. The preserved successful-command cases verify all aligned bytes for each erase size; existing header overlap, partial publication and conflict tests remain. Four scenarios fail against the old adapter and pass with strict Clang and GCC. The existing Python module lacked a script entry point; the new host-only Bazel target and `unittest.main()` ensure these tests actually execute when run directly.
