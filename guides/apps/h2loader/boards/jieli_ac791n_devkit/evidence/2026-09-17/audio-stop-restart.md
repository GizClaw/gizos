# Audio provider stop/restart cycles — 2026-09-17

## Outcome and source

The AC791N DevKit board audio provider survived 10 and then 50 controlled stop → restart cycles of speaker playback and microphone capture with no leak, no stuck writer or drainer and no dropped callback: both runs of the new `audio-stop-restart` diagnostic (Issue #450) printed `result=ok` on every cycle line and on the summary line, heap free stayed at exactly `7171688` bytes from the end of cycle 1 to the end of the last cycle, the SDK task count stayed at `16` on every cycle, every stop completed through the normal `h2_smoke_audio_system_stop()` path on the first attempt, and the provider idle probe reported no open track, no retained operation, no PCM ring storage, no SDK server handle, microphone closed and speaker stopped after every stop. Tested source is `origin/main` `4fd6e947` plus the code commits `d15729d0`, `3b60e9a0`, `d58bf309`, `031b5da4` and `705bd197` on branch `jieli/audio-stop-restart` (provider idle probe, smoke stream counters, cycle diagnostic, bounded cycle flag, host fixtures); the only later commits on the branch add this page and the board guide text and change no built file, which `git diff 705bd197 HEAD --stat -- . ':!guides'` confirms is empty. The board is UID `d879349abc9f` on `/dev/cu.usbserial-20131240` at 460800, and every install went through the UART Loader into Partition 2 with no USB download, format or manual power cycle.

The diagnostic package built from `705bd197` with the default N=10 is SHA-256 `be7ecd2806ea5601b12d595745e2b409a1ad38a51a5869ac6f1847876fb1cb6b` (image `f660cf32b3b4b39fadf961de6d9e73c820136f028a27aadbeff2f4cb32b73e78`), and the N=50 package built with `--//projects/example/targets/h2loader_tar_zlib/audio-system/jieli_ac791n_devkit:stop_restart_cycles=50` is SHA-256 `0b7e502e1222181c4caad2dbc797e68a7f64cb62d5034b44af22244068687509` (image `6a5b95429303740b034487c6c610543a4cc23a33dba0f5ae76352a32f50f0f74`); an earlier pair built from `031b5da4` (packages `f80f53bf…` and `a73eda3a…`) had produced the same 10/10 and 50/50 outcome with identical heap and task figures before the cycle flag was bounded, and only the final pair is recorded below; both were built natively in the `embed-zig-noble-amd64` OrbStack machine with `--config=ac791n --symlink_prefix=bazel-amd64-`, alongside the unchanged `audio_system_package`, and the generated `h2_audio_stop_restart_config.h` carried `10u` and `50u` respectively.

The 144000-byte drop from `heap_baseline=7315688` to `heap_ref=7171688` and the one extra task from `tasks_baseline=15` to `tasks_ref=16` occur once, during cycle 1, and never grow afterwards; they are the SDK audio server's first-open allocations and its persistent server task, which is why the diagnostic takes its references at the end of cycle 1 while still printing the baseline.

Host evidence on the same revision: `//tools/bazel:jieli_audio_lifecycle_test` gained `cycles` (50 fake-SDK open/close cycles with balanced malloc/free, zero live servers and an all-zero idle probe), `cycle_blocked_write` (a `UINT32_MAX` write released with `H2_AUDIO_ERR_INVALID_STATE` by the normal stop path, then a clean restart) and `cycle_stale_callback` (retired encoder and decoder tokens rejected after restart while the new session streams); all three fail to compile against `main`'s provider and pass with Clang, GCC 13.3 in `embed-zig-noble-amd64` and Clang TSan, and `//tools/bazel:jieli_target_runtime_lifetime_test` covers the cycle entry's worker handshake, Runtime release, bounded-cleanup retention and single-stop retry.

## Boundaries

This round proves only stop/restart of the whole audio-system scene through `h2_smoke_audio_system_stop()` and `h2_smoke_audio_system_run()` with a 3 s stream per cycle on one board; it does not cover stop while a PAL writer is blocked on hardware (host-only), drain timing at the DAC, injected SDK failures, concurrent volume changes, BLE or Wi-Fi activity during cycling, or power-loss behaviour, and the audible output was not judged by ear. The `stop_ms` spread up to 991 ms in the N=50 run comes from the SDK decoder STOP/close requests, not from the provider gate, and stays far below the 1000 ms writer deadline; it is recorded, not explained.
