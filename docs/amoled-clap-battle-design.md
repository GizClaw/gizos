# AMOLED《气决》游戏实现文档 v0.2

> 名称：气决
> 目标设备：`boards/amoled/esp32s3`
> 实际屏幕与触摸分辨率：368 × 448，竖屏
> 本阶段目标：完成单机对 AI 的一屏式可玩原型，并为后续 Sprite Maker 素材生成定义统一规格。

## 1. 游戏概念

这是一个把“防、聚气、气功波”拍手游戏做成第一人称小型对战的回合制游戏。当前界面提供聚气、发波、吸收、防御四个转盘入口；首轮规则仍先验证传统三种动作的克制关系，“吸收”的消耗与判定留到真实战斗机制阶段确定。

- 防御：挡住气功波，但会让对手安全聚气。
- 聚气：增加 1 格气，但会被气功波命中。
- 气功波：消耗 1 格气；命中正在聚气的对手，防御可以挡住它。

设计关键词：**一眼看懂、单手操作、每回合约 1.5 秒、黑底高对比、第一人称冲击感**。

## 2. MVP 规则

### 2.1 基础数值

| 项目 | MVP 数值 |
| --- | ---: |
| 玩家 / AI 生命 | 5 点 |
| 初始气 | 0 格 |
| 最大气 | 10 格 |
| 普通气功波消耗 | 1 格 |
| 普通气功波命中伤害 | 1 点 |
| 获胜条件 | 对方生命归零 |

0 气时，“气功波”图标保持可见但置灰并上锁；滑动时可以经过它，但不能确认。这样玩家能理解基础三招关系，又不会因误触浪费一回合。吸收在本阶段只验证图标、转盘和选中状态，不参与下表的胜负判定。

### 2.2 胜负判定

| 玩家出招 | AI：防御 | AI：聚气 | AI：气功波 |
| --- | --- | --- | --- |
| **防御** | 无事发生 | AI +1 气 | 挡住；AI -1 气 |
| **聚气** | 玩家 +1 气 | 双方各 +1 气 | 玩家受 1 伤；AI -1 气 |
| **气功波** | 被挡；玩家 -1 气 | AI 受 1 伤；玩家 -1 气 | 对消；双方各 -1 气 |

AI 必须在玩家确认前确定本回合动作，避免形成“读输入作弊”的感觉。第一版采用带权随机：0 气时以聚气为主；有气时提高气功波概率；玩家连续聚气时略微提高出波概率。

## 3. 一局流程

```text
进入战斗
   ↓
待选择（背景与角色持续待机）
   ↓ 左右滑动
技能转盘吸附到当前技能
   ↓ 点击中央技能图标
锁定双方出招（100 ms）
   ↓
动作前摇（约 250 ms）
   ↓
碰撞 / 判定 / 命中（约 400 ms）
   ↓
结算生命与气槽（约 250 ms）
   ↓
有人生命为 0？── 是 → 胜负演出 → 再来一局
   │
   否
   └────────────→ 下一回合
```

目标节奏：从点击确认到重新可操作不超过 1.1 秒；完整选择加演出平均 1.5～2 秒。

## 4. 屏幕布局

界面采用 368 × 448 的固定设计坐标；实现时不做手机式响应布局，只保留四周 12 px 安全边距。

| 区域 | Y 范围 | 内容 |
| --- | ---: | --- |
| 顶部状态 | 0～48 | 玩家 / AI 生命，回合提示 |
| 第一人称战斗区 | 48～292 | 对手、玩家双手、背景与主要特效 |
| 聚气弧槽 | 286～342 | 沿转盘上沿排布的 10 格气 |
| 技能转盘 | 318～448 | 中央当前技能、左右相邻技能、滑动与点击热区 |

布局原则：

- 当前技能图标直径约 82 px，点击热区至少 96 × 96 px。
- 左右相邻图标约 48 px，透明度约 45%；靠屏幕边缘叠加渐隐遮罩。
- 聚气槽是 10 个独立梯形 / 六边形格，沿椭圆上半弧排列；亮格从左向右填充。
- 战斗区不放常驻文字，避免遮挡第一人称演出。
- 双方生命各用 5 个等宽、等高的倾斜格表示，比分一眼可读。

低保真线框图见 [amoled-clap-battle-wireframe.svg](design/amoled-clap-battle-wireframe.svg)，气氛稿生成提示词见 [amoled-clap-battle-concept-v1.prompt.md](design/amoled-clap-battle-concept-v1.prompt.md)。最终确认的视觉母版由 App 的 `assets/source/approved-mockup.png` 持有。

## 5. 转盘交互

### 5.1 手势

- 只在屏幕下方 150 px 内响应横向滑动，避免战斗区的触摸误判。
- 横向位移超过 36 px，或释放速度超过 0.30 px/ms，切换一格。
- 拖动过程中三个图标按手指位移实时移动、缩放、渐隐；松手后用 160 ms 的 ease-out 吸附。
- 点击中央大图标确认本回合动作。
- 演出期间锁定输入；结算结束后恢复。

### 5.2 触觉与声音（设备支持时）

- 切换技能：轻微“咔”声。
- 确认出招：短促低频提示。
- 聚气成功：音高上扬一阶。
- 挡住 / 对消 / 命中：分别使用金属闷响、能量爆裂、重击三种反馈。

## 6. 中央第一人称动画

动画分成四层，从后向前绘制：动态背景 → 对手 → 战斗特效 → 玩家双手。UI 状态栏和转盘始终在最上层。

### 6.1 持续运动的背景

背景不能完全静止，否则小屏会像一张壁纸；也不应大幅运动，否则会抢走出招注意力。

| 层 | 表现 | 循环方式 | 建议帧率 |
| --- | --- | --- | ---: |
| 远景 | 星点 / 细尘缓慢横移 | 2 张无缝图，每秒 2～4 px | 15 fps |
| 中景 | 能量柱或墙面灯带轻微明暗 | 8 帧 ping-pong | 12 fps |
| 地面 | 透视网格向玩家方向滚动 | Y 偏移循环，每秒 8～12 px | 20～30 fps |
| 待机 | 对手上下 2 px，玩家双手上下 3 px | 1.2 s / 1.6 s 正弦循环 | 30 fps |

静态 UI 每 30 秒整体进行 1 px 的缓慢位置漂移，降低 AMOLED 长时间显示产生残影的风险。背景黑色建议用 `#000000`，非必要区域不铺深灰整块。

### 6.2 聚气动画（总长约 900 ms）

1. `0～150 ms`：玩家双手向内合拢，对手若聚气也进入对应姿态。
2. `150～600 ms`：12～20 个小粒子从画面边缘沿曲线吸向掌心；掌心光球从 10 px 放大到 42 px。
3. `600～760 ms`：光球压缩并闪亮一次，背景亮度短暂下降以突出能量。
4. `760～900 ms`：新增的气槽格从 60% 放大到 115%，再回弹到 100%。

若被气功波命中，聚气在约 360 ms 时被打断：粒子反向散开、双手被冲开、屏幕红色边缘闪烁 100 ms，不增加气。

### 6.3 防御动画（总长约 800 ms）

1. `0～140 ms`：左右前臂迅速交叉到画面中央。
2. `140～260 ms`：半透明六边形盾从 30% 放大到 100%。
3. `260～520 ms`：若挡住气功波，盾面出现白色冲击点和两圈扩散波纹，画面横向震动 2 px；若没有攻击，仅保持微弱呼吸光。
4. `520～800 ms`：盾碎成细光点，双手回到待机位置。

盾牌中心要保持透明，玩家仍能看到对手，避免整个战斗区被一块亮色遮住。

### 6.4 气功波动画（总长约 950 ms）

1. `0～180 ms`：双手拉回，掌间形成 24 px 光核。
2. `180～340 ms`：光核压缩、边缘抖动，亮度升高。
3. `340～650 ms`：双手前推；气功波从玩家近景向对手快速缩小并移动，尾焰用 4～6 帧循环。
4. `650～820 ms`：根据判定播放命中、盾挡或双方对消。
5. `820～950 ms`：亮度恢复，手部复位，气槽扣除 1 格。

三种结果：

- 命中聚气：对手后仰，白闪 1 帧，再出现 6～10 个爆散碎片。
- 撞上防御：波在盾前被压扁，沿盾面向两侧散开。
- 双波对消：画面中心生成一颗快速膨胀后收缩的能量球，双方都轻微后坐。

分镜参考见 [amoled-clap-battle-motion-board.svg](design/amoled-clap-battle-motion-board.svg)。

## 7. 美术与 Sprite Maker 资产规格

先用统一母版生成，再由构建工具缩放 / 转换，避免同一素材多次生成造成风格漂移。

| 资产 | 母版建议 | 运行时建议 | 数量 / 帧数 |
| --- | --- | --- | ---: |
| 四技能图标 | 128 × 128，透明 PNG | 88 px 主图标、52 px 侧图标 | 4 |
| 对手角色 | 192 × 256 / 帧，透明 PNG | 96 × 128 | 待机 6、防 6、聚 10、波 10、受击 6 |
| 玩家左 / 右手 | 192 × 192 / 帧，透明 PNG | 单侧约 128 × 128 | 每动作 6～10 |
| 能量粒子 | 64 × 64，透明 PNG | 16～48 px 缩放 | 8 种 |
| 盾牌 | 256 × 256，透明 PNG | 140～190 px | 6 帧或程序缩放 |
| 气功波与尾焰 | 192 × 192，透明 PNG | 40～160 px | 主体 6、尾焰 6 |
| 对消爆点 | 256 × 256，透明 PNG | 80～180 px | 8 帧 |
| 背景 | 736 × 488 分层母版 | 368 × 244 | 远 / 中 / 地面 3 层 |

生成规范：

- 所有角色和特效使用相同相机：略低机位、对手正面、第一人称手臂从下方进入。
- 不在角色图中生成文字、数字、血条和气槽；这些由 Lua Display DSL 合成，保证状态可独立更新。
- 透明图边缘不要带黑底晕边；特效可保留柔和 alpha，但最终需要检查 RGB565 上的色带。
- 帧动画保持角色脚底锚点、手掌中心锚点稳定。
- 视觉稿使用青色 / 紫色 / 橙色；最终每种技能固定主色：防御青、聚气金、气功波紫。

建议命名：

```text
skill_defend.png
skill_charge.png
skill_wave.png
enemy_idle_00.png ... enemy_idle_05.png
enemy_defend_00.png ...
hands_charge_left_00.png / hands_charge_right_00.png ...
fx_shield_00.png ...
fx_wave_core_00.png ...
fx_wave_tail_00.png ...
bg_far.png / bg_mid.png / bg_floor.png
```

## 8. 技术实现建议

Desktop 与 AMOLED target 执行同一份 Lua resource，并以 RGB565 向 368 × 448 Display 输出。最终结构使用“Lua Display DSL 负责状态和动效 + 代码内 ARGB4444 资源负责角色与 UI 美术”，不读取运行时 PNG，也不依赖浏览器。

```text
game_screen
├── background_layer（3 个循环图层）
├── enemy_layer（角色 sprite）
├── fx_layer（盾、粒子、气功波）
├── hands_layer（第一人称双手）
└── hud_layer
    ├── health_hud
    ├── qi_arc（10 个独立格）
    └── skill_carousel（left / current / right）
```

核心模块建议：

- `game_state`：生命、气、回合、双方选择、胜负判定；纯逻辑、可单元测试。
- `game_ai`：在提交前生成 AI 选择；输入只有当前局面和随机种子。
- `game_view`：通过 Lua Display DSL 更新 HUD 与嵌入式美术资源。
- `game_input`：识别滑动、吸附、点击确认和输入锁。
- `game_animator`：按毫秒时间线驱动精灵帧、位置、缩放与透明度。
- `game_assets`：统一资源索引，屏蔽文件系统路径与图片格式。

性能预算：

- 逻辑与转盘目标 30 fps；精灵序列可用 12～15 fps，但位移动画保持 30 fps。
- 屏幕同时活动粒子不超过 20 个；对象池复用，不在每回合频繁分配。
- 大面积透明叠加最多 2 层；全屏闪光用调色 / 遮罩对象，不播放全屏视频。
- 背景尽量只移动窄条或局部区域，减少 368 × 448 全屏刷新的带宽。
- 运行时素材打包为代码内 ARGB4444，合成后由 Display PAL 以 RGB565 提交；正式性能以真机帧率自检为准。

## 9. 状态机与数据模型

```c
typedef enum {
    GAME_ACTION_CHARGE,
    GAME_ACTION_WAVE,
    GAME_ACTION_ABSORB,
    GAME_ACTION_DEFEND,
} game_action_t;

typedef enum {
    GAME_PHASE_SELECT,
    GAME_PHASE_REVEAL,
    GAME_PHASE_RESOLVE,
    GAME_PHASE_RESULT,
    GAME_PHASE_OVER,
} game_phase_t;

typedef struct {
    uint8_t player_hp;
    uint8_t enemy_hp;
    uint8_t player_qi;
    uint8_t enemy_qi;
    uint16_t round;
    game_phase_t phase;
} game_state_t;
```

判定函数保持无 UI 依赖：输入当前状态、双方动作，输出新状态和一个演出结果枚举（命中、格挡、对消、聚气成功等）。这样规则可在桌面测试，不需要每次烧录设备。

## 10. MVP 验收标准

- 聚气、发波、吸收、防御四个技能可通过左右滑动循环选择，松手后稳定吸附。
- 0 气不能确认气功波；气始终限制在 0～10。
- 9 种出招组合判定正确，并有自动化单元测试。
- 生命降至 0 后停止接收战斗输入，并显示胜负与重开入口。
- 背景、对手和双手在待机时持续有轻微运动。
- 聚气、防御、气功波各有可区分的完整动画；命中、格挡、对消表现不同。
- 真机连续运行 10 分钟无明显内存增长，交互阶段平均达到 30 fps。

## 11. 推荐开发顺序

1. 用纯色几何占位完成规则、AI、转盘、气槽和生命显示。
2. 用简单圆、线和缩放先打通三条动画时间线。
3. 使用已确认的四技能图标、完整对手和第一人称双手制作源生成 ARGB4444 资源。
4. 生成并接入特效与三层背景，完成 RGB565 / alpha 真机检查。
5. 调整音效、屏幕震动、回合节奏和 AI 权重。
6. 增加可选进阶规则：2 气强化波、蓄满必杀、角色皮肤或双人联机。

## 12. 下一阶段需要确定的内容

- “Spirit Maker”是否指 **Sprite Maker**，以及具体使用的是哪个网站 / 应用；不同工具的提示词和导出能力差异较大。
- 角色世界观：校园夸张风、机甲格斗风、武侠气功风，或更抽象的能量人形。
- 首发只做单机 AI，还是需要蓝牙 / 网络双人对战。
- 是否使用设备音频和震动 / IMU 手势；它们可以增强“拍手游戏”的实体感，但不应阻塞触屏 MVP。
