# Independent Alipay network binding client

The default `:alipay_independent` target exports self-implemented original-API entry points using the exact caller-owned public headers. Set `ALIPAY_API_PATH` and pass `--repo_env=ALIPAY_API_PATH`; [the header-only import](../../../third_party/alipay/api_repository.bzl) validates every header against its manifest and reads no archive or vendor implementation. It selects network `alipay_bind.h`; BLE binding is a different, mutually exclusive header profile. Business callers retain original names, parameter types, callback structures and constants.

The lower-level `:client` and `:protocol` targets implement the child-watch network/ECDH binding-code profile without vendor headers, archives or calls. [h2_alipay_client.h](include/h2_alipay_client.h) owns blocking registration and prepareBind; [h2_alipay_protocol.h](include/h2_alipay_protocol.h) owns protobuf encoding, identity-key derivation, canonical request bytes, HMAC-SM3, JSON construction and binding payload formatting. The qualified profile is product type 3 with `PAYCODE | SQUARE` (`0x4001`).

| Original entry | Independent status |
| --- | --- |
| `alipay_pre_init` | Local idempotent initialization after injected PAL configuration |
| `alipay_get_binding_code` | Self-implemented registration, persistence, signing and prepareBind |
| `alipay_get_binding_status` | False; independent account completion is not yet implemented |
| `alipay_query_binding_result` | Explicit nonzero failure; no fake success or vendor fallback |
| Payment, provisioning, unbind and other declared entries | Not implemented or exported yet |

Exact headers establish source/ABI compatibility for implemented entry points, not complete SDK behavior. The optional [configuration facade](include/h2_alipay_independent.h) injects PAL and retains the pending token/private key until release or another code request. SDK-compatible errors are nonzero on failure. Releasing the facade wipes memory without a server request or persistent deletion. It contains no diagnostic ring or logging layer; integration code observes invocation and transport results. Unsupported operations must be implemented and qualified before replacing their vendor counterparts.

Both targets expose portable public interfaces and return payload text. They do not encode QR/barcode matrices, draw pixels, operate displays, select boards, read factory storage or start modems. Callers inject identity, product configuration, storage namespace and PAL capabilities; App code owns presentation, and final artifact entries own physical identity acquisition and platform assembly. The child-watch prefixes and feature restriction describe an Alipay protocol profile independently of any physical board.

The current delivery places the P-256 public point in `ecdhFactor`. Its `clientKey`, `imei`, `imsi` and `appProductVersion` fields use the selected IMEI identity text. This implementation preserves those observed bytes. P-256 generation and SEC1 public-point export use Crypto PAL; SM3/HMAC, SHA-256 and base64 remain portable. JSON allocations use the caller's Memory PAL through yyjson.

A dedicated caller-selected Pref namespace stores one versioned record containing the device name, business identifier and an identity fingerprint. A different SN/IMEI/MAC/model/company rejects that record rather than silently using another identity's state. SDK namespaces remain separate. The first call registers through `iothub.internal.device.active`; later calls reuse persisted state. Commit failure prevents prepareBind. HTTPS, HTTP status, `Result-Status`, JSON success and the token are checked independently, without retries.

The core's returned private key and token are pending binding state. Retain the result while displaying its code and use `h2_alipay_client_result_clear()` when that lifetime ends; the original-API facade owns that lifetime internally. Errors clear code, token and private key while preserving operation results. The library never exports raw requests, signatures, identity values or tokens through logs. SDK adaptation, bounded tracing, backend selection and the test App live under [the integration suite](../../../projects/testing/integration/alipay/README.md); production code has no dependency back to it.

Run `:protocol_test`, `:client_test` and `//libs/crypto/sm3:sm3_test` for offline behavior. The manual `:sdk_differential_test` compiles the pinned original Xtensa objects and independent C together under caller-supplied Espressif QEMU, with networking disabled. Set `ALIPAY_XTENSA_CC` and `ALIPAY_QEMU` and pass them with `--test_env`; select the original SDK with `ALIPAY_SDK_PATH` and `--repo_env=ALIPAY_SDK_PATH`. It compares synthetic SM3-HMAC inputs, canonical bytes, timestamps, identity-derived signatures, registration protobuf, prepareBind JSON and binding payloads. Only test-copy symbol visibility and fixture boundaries change; executable sections and original archive hashes are checked. The manual comparison test has vendor inputs; neither production target does. This does not establish complete SDK equivalence.

Run `:sdk_compatible_test` and `:sdk_compatible_cpp_test` with only `ALIPAY_API_PATH` selected to compile unchanged original C/C++ declarations against the self-implemented facade. These test real independent protocol calls with controlled PAL fixtures, lifecycle/reentry and explicit unsupported completion; no vendor archive is linked.
