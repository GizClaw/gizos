# Independent Alipay network binding client

The default `:alipay_independent` and `:protocol` targets implement the current child-watch network/ECDH binding-code profile without vendor headers, archives or calls. [h2_alipay_client.h](include/h2_alipay_client.h) owns blocking registration and prepareBind; [h2_alipay_protocol.h](include/h2_alipay_protocol.h) owns protobuf encoding, identity-key derivation, canonical request bytes, HMAC-SM3, JSON construction and binding payload formatting. The qualified profile is product type 3 with `PAYCODE | SQUARE` (`0x4001`). Binding polling/completion, provisioning, unbind, reset and payments are not implemented.

Both targets expose portable public interfaces and return payload text. They do not encode QR/barcode matrices, draw pixels, operate displays, select boards, read factory storage or start modems. Callers inject identity, product configuration, storage namespace and PAL capabilities; App code owns presentation, and final artifact entries own physical identity acquisition and platform assembly. The child-watch prefixes and feature restriction describe an Alipay protocol profile independently of any physical board.

The current delivery places the P-256 public point in `ecdhFactor`. Its `clientKey`, `imei`, `imsi` and `appProductVersion` fields use the selected IMEI identity text. This implementation preserves those observed bytes. P-256 generation and SEC1 public-point export use Crypto PAL; SM3/HMAC, SHA-256 and base64 remain portable. JSON allocations use the caller's Memory PAL through yyjson.

A dedicated caller-selected Pref namespace stores one versioned record containing the device name, business identifier and an identity fingerprint. A different SN/IMEI/MAC/model/company rejects that record rather than silently using another identity's state. SDK namespaces remain separate. The first call registers through `iothub.internal.device.active`; later calls reuse persisted state. Commit failure prevents prepareBind. HTTPS, HTTP status, `Result-Status`, JSON success and the token are checked independently, without retries.

The returned private key and token are pending binding state. Retain the caller-owned result while displaying its code and use `h2_alipay_client_result_clear()` when that lifetime ends. Errors clear code, token and private key while preserving numeric stage and transport diagnostics. The library never exports raw requests, signatures, identity values or tokens through logs.

Run `:protocol_test`, `:client_test` and `//libs/crypto/sm3:sm3_test` for offline behavior. The manual `:sdk_differential_test` compiles the pinned original Xtensa objects and independent C together under caller-supplied Espressif QEMU, with networking disabled. Set `ALIPAY_XTENSA_CC` and `ALIPAY_QEMU` and pass them with `--test_env`; select the original SDK with `ALIPAY_SDK_PATH` and `--repo_env=ALIPAY_SDK_PATH`. It compares synthetic SM3-HMAC inputs, canonical bytes, timestamps, identity-derived signatures, registration protobuf, prepareBind JSON and binding payloads. Only test-copy symbol visibility and fixture boundaries change; executable sections and original archive hashes are checked. The manual comparison test has vendor inputs; neither production target does. This does not establish complete SDK equivalence.
