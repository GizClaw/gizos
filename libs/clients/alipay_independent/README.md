# Independent Alipay client

The default `:alipay_independent` target exports self-implemented original-API entry points using the exact caller-owned public headers, including the original company/model identity declarations. Set `ALIPAY_API_PATH` and pass `--repo_env=ALIPAY_API_PATH`; [the header-only import](../../../third_party/alipay/api_repository.bzl) validates every header against its manifest and reads no archive or vendor implementation. It selects network `alipay_bind.h`; BLE binding is a different, mutually exclusive header profile. Every implemented original entry is declared by and compiled against its unchanged original header; names, parameter types, return types, callback structures and C/C++ linkage must match. Do not redeclare an approximate SDK signature or expose a legacy CSI substitute for a current alipay entry.

The lower-level `:client` and `:protocol` targets implement the child-watch network/ECDH binding profile without vendor headers, archives or calls. [h2_alipay_client.h](include/h2_alipay_client.h) owns blocking registration, prepareBind, queryBindInfo, ECDH material processing, finishBind, binding storage, local payer-code generation and payment-result queries; [h2_alipay_protocol.h](include/h2_alipay_protocol.h) owns protobuf encoding, identity-key derivation, canonical request bytes, HMAC-SM3, JSON construction and binding payload formatting. The qualified profile is product type 3 with `PAYCODE | SQUARE` (`0x4001`).

| Original entry | Independent status |
| --- | --- |
| `alipay_pre_init` | Local idempotent initialization after injected PAL configuration |
| `alipay_get_companyName`, `alipay_get_productModel` | Read injected local manufacturer/model after configure, including before initialization |
| `alipay_get_binding_code` | Self-implemented registration, persistence, signing and prepareBind |
| `alipay_get_sn`, `alipay_get_imei`, `alipay_get_mac`, `alipay_get_productType` | Return injected identity and explicit device classification |
| `alipay_get_binding_status` | True only for a validated completion record in the injected store |
| `alipay_query_binding_result` | Signed queryBindInfo, validated factors, ECDH, staged persistence, finishBind and committed/read-back completion |
| `alipay_get_paycode` | Local double AES-CBC seed decryption, bounded parsing, HMAC-SHA1 HOTP and original decimal packing |
| `alipay_query_order_result_string` | Signed queryOrderStatus, bounded result parsing, success ACK and server-requested local binding deletion |
| Tap-payment, provisioning, standalone unbind and other declared entries | Not implemented or exported yet |

Exact headers establish source/ABI compatibility for implemented entry points, not complete SDK behavior. The optional [configuration facade](include/h2_alipay_independent.h) injects PAL and serializes original calls through Sync PAL. The delivered query wrapper returns zero for an initialized query and communicates pending/network failure through `ALIPAY_STATUS_UNKNOWN`, completion through `ALIPAY_STATUS_BINDING_OK`, and other failures through `ALIPAY_STATUS_BINDING_FAIL`. The independent facade preserves this convention and exposes separate non-secret PAL diagnostics. Other entry failures map to nonzero results; detailed vendor error-code equivalence is not claimed. Releasing the facade wipes memory without a server request or persistent deletion.

The six identity getters use injected configuration, including before initialization; they perform no network, storage or hardware operation. String capacities include a NUL byte and successful lengths exclude it. Short buffers preserve their bytes and input length. String getters fail before configure/after release; the return-only type getter uses `UINT32_MAX` in that state. Device classification is explicit configuration: type 3 is supported by the current protocol; other profiles return `UNSUPPORTED` instead of sending child-watch fields.

Both targets expose portable public interfaces and return payload text. They do not encode QR/barcode matrices, draw pixels, operate displays, select boards, read factory storage or start modems. Callers inject identity, product configuration, storage namespace and PAL capabilities; App code owns presentation, and final artifact entries own physical identity acquisition and platform assembly. The child-watch prefixes and feature restriction describe an Alipay protocol profile independently of any physical board.

The current delivery places the P-256 public point in `ecdhFactor`. Its `clientKey`, `imei`, `imsi` and `appProductVersion` fields use the selected IMEI identity text. This implementation preserves those observed bytes. P-256 generation, SEC1 public-point validation/export and ECDH use Crypto PAL; SM3/HMAC, SHA-256 and base64 remain portable. JSON allocations use the caller's Memory PAL through yyjson.

A dedicated caller-selected Pref namespace stores one versioned record containing the device name, business identifier and an identity fingerprint. A different SN/IMEI/MAC/model/company rejects that record rather than silently using another identity's state. SDK namespaces remain separate. The first call registers through `iothub.internal.device.active`; later calls reuse persisted state. Commit failure prevents prepareBind. HTTPS, HTTP status, `Result-Status`, JSON success and the token are checked independently, without retries.

A separate `binding` Pref value uses a versioned, explicitly encoded record with identity fingerprint, phase, TID/UID, nickname/login, shared secret, seed and corruption digest. It stages validated material and a resume token before finishBind, then commits and reads back completion before reporting bound. The seed accepts 16–128 bytes, matching the original ECDH parser's decoded seed buffer; factors require an exact 64-byte P-256 X/Y point, `&`, and strict even-length hex seed. Serialized storage covers the combined maximum field lengths, including the staged token. Both coordinates are validated through Crypto PAL. This follows the delivered ECDH format and does not introduce an AES decryption step. The injected store must provide the product's required protection for sensitive values; the corruption digest is not authentication or encryption.

One explicit query makes at most queryBindInfo and finishBind requests; the library performs no automatic polling. Pending/transport failure retains the session. A failed staged commit sends no finish. A failed final commit after an acknowledged finish retries locally within the same session. Restarted staged state reports `NEEDS_VERIFICATION`; an explicit query can retry finish from its persisted token without deriving factors again. A crash or lost acknowledgement can cause repeated finish RPCs; exactly-once server behavior is not claimed. Completed state restores locally without any RPC. Existing complete/staged records block a fresh code from replacing them. No reset, standalone unbind or debit request is performed.

The core's returned private key and token are pending binding state. Retain them for query or clear them with `h2_alipay_client_result_clear()` on cancellation; the facade owns that lifetime internally. The private key is wiped after durable factor staging, the completed session is cleared, and JSON/workspace buffers are wiped on release. Query failures preserve only the state needed for a retry. The library has no logging or platform dependency; integration owns bounded traces and the test App, and final entries own hardware identity acquisition and PAL assembly.

Run `:protocol_test`, `:client_test`, `:binding_test` and `//libs/crypto/sm3:sm3_test` for offline behavior. The manual `:sdk_differential_test` compiles the pinned original Xtensa objects and independent C together under caller-supplied Espressif QEMU, with networking disabled. Set `ALIPAY_XTENSA_CC` and `ALIPAY_QEMU` and pass them with `--test_env`; select the original SDK with `ALIPAY_SDK_PATH` and `--repo_env=ALIPAY_SDK_PATH`. It compares synthetic SM3-HMAC inputs, canonical bytes, timestamps, identity-derived signatures, registration protobuf, prepareBind JSON, binding payloads and the original query wrapper status mapping. Only test-copy symbol visibility and fixture boundaries change; executable sections and original archive hashes are checked. The manual comparison test has vendor inputs; neither production target does. This does not establish complete SDK equivalence.

Run `:sdk_compatible_test` and `:sdk_compatible_cpp_test` with only `ALIPAY_API_PATH` selected to compile unchanged original C/C++ declarations against the self-implemented facade. These test real independent protocol calls with controlled PAL fixtures, lifecycle/reentry, completed binding, persistent recovery and original device-info signatures; no vendor archive is linked.


The caller owns storage retention. The integration's default session mode supplies volatile Pref, so committed registration/binding records survive namespace close but not hardware reset. A library completion/snapshot describes validated data in that provider; persistence requires a durable provider and separate restart evidence. No platform or concrete Pref provider is selected here.

## Payer codes and result queries

`alipay_get_paycode` and `alipay_query_order_result_string` compile directly against the unchanged `alipay_pay.h` and `alipay_pay_result.h`. The facade serializes calls, converts lengths through local `size_t` values, and preserves the original `uint32_t *` ABI. The shared integration App uses the same invocation and display flow for both implementations; the independent capability table omits tap operations, so the menu hides them and does not start NFC/BLE.

The ECDH delivery decrypts the seed with two AES-128-CBC/PKCS#7 layers: the last half of the 32-byte binding secret decrypts the outer layer, and the first half decrypts the inner layer. The IV combines decoded MAC bytes with the delivered fixed protocol suffix. Bounded parsing extracts the decimal index, hex HOTP secret and interval. Current 32-bit UTC seconds select the counter; HMAC-SHA1 and the original decimal transformation produce an 18/19-digit payer code. AES-CBC without padding is a generic Crypto PAL operation; padding belongs here. ESP uses its PSA provider, host tests use wolfCrypt, and neither provider is selected by this library. Sensitive workspaces and JSON allocations use injected Memory PAL and are wiped before release.

Result queries use the actual displayed code, current TID/UID, original request signing and verified HTTPS. Pending, confirmed success, failure detail, disabled and server-unbound actions are distinct. Successful queries send the original `payResultAck`; an ACK failure remains separate from the confirmed business outcome. A server `DELSEED`/`DELSEEDANDINDEX` removes only this namespace's binding value, preserving registration. Malformed or oversized data and network failures cannot report paid. The public code generator returns the original 99 for inner generation failures, 4 when unbound, and the original wrong-parameter value for invalid arguments; bounded short-buffer handling avoids relying on undefined vendor overflow behavior.

The manual `:payment_test` covers synthetic seed/key vectors, capacities and guard bytes, time boundaries, padding failures, query/ACK bodies, malformed responses, remote unbinding and failure at each observed query allocation. `:sdk_payment_differential_test` uses the pinned original Xtensa archives in network-disabled QEMU: it compares candidate code bytes and original return cases, and independently verifies original query/ACK bodies and status cases against the host fixtures. Pass `ALIPAY_SDK_PATH`, `ALIPAY_XTENSA_CC`, `ALIPAY_QEMU` and optional `ALIPAY_QEMU_LIBDIR` with `--test_env`; production still uses only the header import. Synthetic differential tests, host provider vectors and firmware builds do not establish real-device payment or settlement.
