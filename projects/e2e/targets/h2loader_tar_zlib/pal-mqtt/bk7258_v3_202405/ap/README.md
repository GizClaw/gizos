# BK MQTT console owner

The standalone launcher uses the existing real PAL physical UART provider for mandatory protocol records. It stops and joins the command service, then configures a console owner before the resource baseline. The provider selects `CONFIG_UART_PRINT_PORT`; the launcher supplies the actual `CONFIG_UART_PRINT_BAUD_RATE` and 8N1/no flow control. It retains RX ownership so SDK shell cannot parse or echo old host iKCP bytes during the suite. Both resource snapshots include this same owner.

Each BOOT/RUN/CASE/SUMMARY/READY record is framed with CRLF in a bounded stack buffer and issued as one write using the provider's existing atomic TX mutex, FIFO-ready checks and SDK TX suspend/resume boundary. The 5-second deadline includes lock contention and FIFO drain. Any nonzero result or short successful prefix is a real output failure; the launcher never retries that prefix as a complete record. This avoids the SDK async log pool and its printf success result without changing the global SDK log configuration or production UART/Net/MQTT providers.

After the suite and its after-snapshot, the complete first ledger is emitted. The launcher performs a bounded physical TX drain, deinitializes the console owner and restarts the control service with a fresh RX ring; stale bytes/overflow cannot transfer to the new command session. Setup, suite, snapshot, write or drain failure still attempts that restoration. Restart/output errors remain failures, and confirmation requires successful prior output and restored management. READY uses the restarted provider's shared atomic writer. If that output channel itself fails, SDK diagnostics emit only an explicit failure; they never declare success. There is no later replay that could replace a broken first ledger.

`//projects/e2e/targets/h2loader_tar_zlib/pal-mqtt/bk7258_v3_202405:ledger_console_test` injects configuration failure, positive short prefix, prefix followed by timeout, drain timeout and restart failure into the real launcher policy, verifies restoration and persistent rejection of confirmation, and checks a record larger than the SDK's 136-byte synchronous buffer is untruncated. These are host policy tests, not broker/device E2E qualification. `//native_component_src/bk7258/ap/h2_pal_core:uart_io_test` separately validates the existing provider's actual bounded write implementation. New hardware qualification still requires two fresh complete first ledgers and the unchanged strict broker/resource/metadata/coredump oracle.
